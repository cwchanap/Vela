## Current main findings and revised decisions (2026-11-16)

- Both `apps/vela` and `apps/vela-mobile` run Quasar app-vite v2 / Vite 7, `@quasar/vite-plugin` v1 in their Vitest configs, Vue Router 4, and Vitest/coverage 3. The WXT extension uses its own toolchain. Previous [#76](https://github.com/cwchanap/Vela/pull/76) tried an isolated plugin bump and failed with `parseSync`.
- Quasar CLI v3 **disables Vite's env loader**. Its default env inputs are `.env` and `.env.local` (the latter outside CI), and its default client prefix is `QCLI_`. `packages/cdk/scripts/inject-env.ts` instead writes `.env.production` and `VITE_*` values for **both** apps. A v3 build can pass while embedding *no* Cognito data if this isn't explicitly addressed.
- Quasar v3's `build.env` is a loader settings object, not the old per-key client env map. In **both** `quasar.config.ts` files, use `build.env: { clientPrefix: 'VITE_', file: ctx.prod ? '.env.production' : [] }`. Existing default `.env`/local files remain eligible; this is an **additional** production file. Preserve the deployed env writer and current `VITE_*` API.
- Mobile's `scripts/sync-ios-version.mjs` and `build/validate-mobile-api-url.ts` each implement old Vite dotenv semantics via direct `dotenv`/`dotenv-expand`. **Remove both loaders and both direct dependencies**, not pin v11 as a third engine and not upgrade to v1000. Use the Quasar-resolved values supplied in `config.define` by the existing build plugin for both production validation and Capacitor MARKETING_VERSION sync. **But two standalone CLI consumers of `loadMobileBuildEnv` must be migrated**: `build/verify-deployed-config.ts` and `build/m1-foundation-harness.ts` run outside Vite and need a tiny dependency-free plain `.env` reader via Node 22 `node:util.parseEnv`, without becoming authoritative for compiled app values. An empty explicit override or `$BASE` interpolation must be checked against the *real* build, not guessed from v2 tests.
- Quasar v3 requires Vue Router 5, `#q-app` instead of `#q-app/wrappers`, imports via `@/`, and a supported Node version. Pin Node **22.22.0**. Two web boot files still use `quasar/wrappers`. The SPA routers do not need the old SSR/hash history ternary.
- Remove unsupported or dead pieces rather than porting them: unused `@quasar/quasar-app-extension-testing` and web `test` block, dead web `manualChunks`, irrelevant web SSR/PWA/Cordova/Electron/BEX mode config, redundant Capacitor Quasar config aliases, and `coverage.all` in both Vitest configs.
- `.github/workflows/build-lint.yml` and `unit-test.yml` support `workflow_dispatch` but skip draft PR triggers. `e2e.yml`'s `mocked-settings` job runs even on drafts. Open [#89](https://github.com/cwchanap/Vela/pull/89) bumps Vitest without matching coverage-v8; do not merge this incomplete change into the migration as-is. #90/#91 are unrelated.

Reviews: [initial design review](https://github.com/cwchanap/Vela/pull/93#pullrequestreview-5925171471) and [follow-up review at `9668d826`](https://github.com/cwchanap/Vela/pull/93#pullrequestreview-5931228564). Vendor: [Quasar v3 upgrade guide](https://quasar.dev/quasar-cli-vite/upgrade-guide/) and [new env behavior](https://quasar.dev/quasar-cli-vite/handling-import-meta-env/).

## End-to-end definition of done

**One PR per HPA-918 ticket.** The migration replaces v2/Vite 7 with a supported Quasar v3/Vite 8 toolchain for both apps, preserves working WXT tests, pins frontend Node, makes Quasar the **only** client-env loading engine, enforces a persistent CI check for both production bundles, and proves native version parity. CI remains the reproducible regression gate; MCP-driven browser E2E of **actual supported states/diagnostic routes** and screenshot visual inspection satisfy UI acceptance. Version parity is verified against resolved build values and native metadata rather than a nonexistent Home-page label. A native Simulator check is performed where available, otherwise disclosed as unverified. No manual/human acceptance, compatibility framework, or separate PR.
